# Design

## Context

Сейчас списки metroGen неоднородны:

- форма создания/правки вставлена **сверху** секции и управляется локальными `showForm`/`editId`
  (`AdminOwnersPage.tsx:97-116`, `AdminMethodologiesPage.tsx:126-207`,
  `AdminEtalonsPage.tsx:158-235`, `AdminAuxInstrumentsPage.tsx:82-111`);
- таблицы не раскрываются (`AdminOwnersPage.tsx:118-147`, `AdminEtalonsPage.tsx:237-289`,
  `GenerationPage.tsx:553-588`);
- редактирование есть только у части сущностей (владельцы — PATCH, методики — PATCH + пункты,
  эталоны — только upsert без PATCH/DELETE, вспом. СИ — только create).

Эталон metroLog:

- карточка-аккордеон: `<button aria-expanded>` + вращающийся шеврон, тело — при раскрытии
  (`metroLog AdminUsersPage.tsx:515-573`, `RepairsPage.tsx:983-1134`);
- дискриминированный union состояния диалогов: `ActiveModal` (`metroLog lib/equipmentRegistry.ts:95-106`)
  плюс `DeleteTarget` для удаления;
- диалог: `Modal` → `AppDialog` → Radix (`metroGen components/ui/app-dialog.tsx`), удаление —
  `DeleteConfirmModal` (уже есть в metroGen).

## Goals / Non-Goals

**Goals:**

- Один и тот же паттерн списка, диалога и удаления на всех справочниках и в реестре.
- Добавление новой сущности (например, методики) — быстро и без «прыгающей» формы.
- Полнота CRUD из UI, с понятными отказами.

**Non-Goals:**

- Не менять схему БД (новых таблиц/колонок нет — только новые эндпоинты).
- Не трогать вендоренные диалоговые примитивы (`ui/dialog.tsx`, `ui/app-dialog.tsx`).
- Не переделывать массовые сценарии генерации (`protocols.py`) — только зона «База данных».
- Не вводить виртуализацию/пагинацию справочников в этом change (списки малы; фильтры уже есть).

## Decisions

### D1: Справочники — карточки-аккордеоны, реестр — раскрывающаяся строка таблицы

- Владельцы, методики, эталоны, вспом. СИ: каждый элемент — `tone-child rounded-2xl border border-line`
  с кнопкой-заголовком (`aria-expanded`, шеврон поворачивается классом `rotate-180`) и телом при
  раскрытии. Шапка показывает ключевые поля, тело — полные реквизиты и действия.
- Реестр генерации остаётся таблицей (много колонок и фильтров): в строку добавляется кнопка
  раскрытия, а при раскрытии под ней рендерится дополнительный `<tr>` с `colSpan` на всю ширину и
  деталями записи. Так фильтры и сортировка не ломаются.

*Альтернатива:* одна раскрытая строка-аккордеон на весь реестр. Отклонено — реестр это таблица с
поиском/фильтрами, и карточки потеряют табличное сравнение колонок.

### D2: Создание/правка — диалог по union-состоянию

На каждой странице — одно состояние вида
`type ActiveModal = null | { kind: "owner"; mode: "create" | "edit"; id?: number } | ...`,
и один `<Modal>` (или два: сущность и вспомогательный редактор). Это повторяет metroLog-паттерн и
не размножает булевы флаги. Форма внутри модалки: `space-y-4`, поля — `label.block text-sm text-steel`
+ `form-input`, футер — `btn-secondary` (отмена) и `btn-primary` (сохранить) через `footer`-слот
`Modal`.

*Альтернатива:* инлайн-форма внутри раскрытой строки. Отклонено как основной паттерн
(пользователь допускал оба): для методик с пунктами и эталонов с десятком полей раскрытая строка
превращается в длинную форму внутри списка, а metroLog-прецедент — диалог. Инлайн оставляем для
точечных действий (например, быстрый тумблер активности в теле строки).

### D3: Удаление — только через `DeleteConfirmModal`

Состояние удаления — `{ id, name } | null`; отказ API (409) показывается в самой модалке
(`errorMessage`), список не меняется.

### D4: Backend — недостающие операции

Добавляем к существующим роутерам:

| Роутер | Есть | Добавляем |
|---|---|---|
| `owners.py` | `GET`, `POST`, `PATCH /{id}` | `DELETE /{id}` (409 при ссылках), `PUT /{id}/aliases` (или в `PATCH` — список алиасов) |
| `methodologies.py` | `GET`, `POST`, `GET /{id}`, `PATCH /{id}` | `DELETE /{id}` (409 при ссылках), управление алиасами |
| `etalons.py` | `GET`, `POST` (upsert) | `PATCH /{id}`, `DELETE /{id}`, `GET /{id}/certifications`, `POST /{id}/certifications`, `DELETE /{id}/certifications/{cid}` |
| `auxiliary_instruments.py` | `GET`, `POST`, `POST /bulk` | `PATCH /{id}`, `DELETE /{id}` |

Правило отказа: удаление сущности, на которую ссылаются другие записи (`MeasuringInstrument`,
`Protocol`, `VerificationRegistryEntry`), возвращает `409` с человекочитаемым сообщением; UI
показывает его в диалоге. Каскадное удаление не вводим.

### D5: Пункты и алиасы — в диалоге сущности

Пункты методики редактируются тем же паттерном, что сейчас (`AdminMethodologiesPage.tsx:152-200`:
таблица со строками, `+ Добавить пункт`, `×`), но переносятся внутрь диалога. Алиасы владельца и
методики — список чипов с добавлением/удалением в том же диалоге.

## Risks / Trade-offs

- [Расхождение поведения списков и реестра] → общий паттерн один, различие (карточка vs строка
  таблицы) зафиксировано в D1 и проверяется на обоих типах.
- [Массовые справочники вырастут и станут тяжёлыми] → сейчас объёмы малы; при росте — отдельный
  change с пагинацией (сейчас у владельцев/эталонов её нет, у реестра есть лимит).
- [409 на удаление ломает привычный сценарий] → это осознанное поведение: лучше понятный отказ, чем
  осиротевшие ссылки; сценарий в спеке.
- [Правки API задевают контракты] → добавляем только новые методы; существующие ответы не меняем.

## Verification

- `npx tsc --noEmit`, `npm run check:ui`, `npm run build` в `frontend/` — зелёные.
- Backend: `pytest` (регрессии роутеров) — зелёный; новые тесты на DELETE/409/PATCH.
- Ручной прогон на stage: добавить методику через диалог, отредактировать пункты, удалить
  используемого владельца (ожидаем 409 в диалоге), раскрыть строку реестра.
