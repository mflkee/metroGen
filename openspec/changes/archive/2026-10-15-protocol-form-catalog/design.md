# Design

## Context

Сейчас:

- каталог форм — словарь `TEMPLATES` в `app/services/templates.py` (6 форм + 2 под-формы уровнемера),
  у каждой только `title` и `path` на HTML-файл; **иерархии нет**;
- привязки — таблица `template_binding_rules` (`instrument_kind`, `match_field` ∈ {`mitype_number`,
  `title_keyword`, `methodology_code`}, `match_value`, `template_id`, `priority`, `is_active`);
- разрешение — `app/services/template_rules.py:resolve_form` (override → правила → форма методики →
  эвристики), предпросмотр — `POST /api/v1/templates/rules/preview`;
- страница показывает плоский список правил; иерархии, обратного поиска и оси «модификация» нет.

Факты из Аршина (полностью — `references/arshin-forms.md`): у одного рег. номера десятки модификаций
(`86065-22` — 10 вариантов написания; `47249-16` — FMP51/52/54/57), методика приходит в разных
редакциях (`МП 47249-16`, `МП 47249-16 с изм.№1`), а МПИ и условия поверки внутри типа зависят от
исполнения.

## Goals / Non-Goals

**Goals:**

- Ответить в UI на вопросы «какие формы есть», «какая база», «что от чего наследуется», «почему
  строка получила эту форму», «что попадёт под правку».
- Ввести ось «модификация» в правила и в инспектор.
- Подготовить модель к редактору (форма как сущность с родителем), не строя сам редактор.

**Non-Goals:**

- Редактирование форм и таблиц (это `protocol-form-editor`).
- Переписывание HTML-шаблонов в данные (шаг редактора).
- Изменение алгоритмов генерации таблиц.

## Decisions

### D1: Форма становится сущностью (`protocol_forms`), наследование — ссылкой на родителя

Новая таблица:

```python
class ProtocolForm(Base):
    id, code (unique)          # совпадает с текущим template_id, напр. "level_meter"
    title: str
    instrument_kind: str       # manometers | controllers | thermometers | level_meters
    parent_code: str | None    # наследование: "level_meter_two_tables" → "level_meter"
    renderer: str              # "html" (app/templates/*) | "data" (структура в БД, шаг редактора)
    structure: JSON | None     # появится в protocol-form-editor
    notes: str | None
    is_active: bool
```

Миграция сидит её из текущего `TEMPLATES`; для под-форм уровнемера прописывается родитель
`level_meter`. `template_binding_rules.template_id` продолжает ссылаться на код формы — совместимо.

*Альтернатива:* выводить иерархию из кода статически (в Python). Отклонено — редактору всё равно
нужна сущность, а наследование должно быть видно и правиться без деплоя.

### D2: Ось «модификация» в правилах

`MATCH_FIELDS` дополняется `modification`; сравнение — нормализованное и по вхождению:

```python
def _normalize_modification(value: str) -> str:
    text = value.upper()
    for junk in ("МОД.", "МОД ", "ИСП.", "ИСП ", "МОДИФИКАЦИЯ"):
        text = text.replace(junk, " ")
    return re.sub(r"\s+", " ", text).strip()
```

Матч: нормализованное `match_value` входит в нормализованную модификацию строки. Это позволяет одним
правилом поймать `FMP51`, `Levelflex FMP51`, `мод. FMP51`.

*Альтернатива:* точное равенство. Отклонено — Аршин не нормализует написание (см. факты выше).

### D3: Граф — force-directed на `d3-force` + собственный SVG

Узлы: формы (база/производная) и «якоря» осей (тип прибора, методика, модификация — как узлы-условия
из правил). Рёбра: `parent_code` (наследование) и правила (условие → форма).

- раскладка — `d3-force` (маленькая библиотека без DOM-зависимостей), рендер — SVG вручную;
- поиск подсвечивает совпадения и «подтягивает» их к центру (как в Obsidian);
- фильтры: тип прибора, ось (методика/тип/модификация), статус правила (вкл/выкл), происхождение
  (данные/HTML);
- клик по узлу-форме → панель формы (родитель, дети, правила, которые в неё ведут).

*Альтернатива A:* `cytoscape`/`react-flow` — мощнее, но тяжелее и навязывает свой UI-стиль; флот
держит зависимости минимальными. *Альтернатива B:* слоистая раскладка без физики — проще, но не
даёт «обсидианового» ощущения, которого просит владелец.

### D4: Инспектор решения возвращает путь, а не только ответ

`POST /api/v1/templates/rules/preview` расширяется:

```json
{
  "template_id": "level_meter_two_tables",
  "source": "rule",
  "rule_id": 12,
  "steps": [
    {"stage": "override", "matched": false},
    {"stage": "rule", "matched": true, "rule_id": 12, "match_field": "modification", "match_value": "901.1"},
    {"stage": "methodology", "matched": false},
    {"stage": "fallback", "matched": false}
  ]
}
```

Фронтенд подсвечивает по `steps` путь на графе — так «почему» становится наглядным.

### D5: Обратный поиск — из правил, а не из реестра

Панель формы показывает правила, которые на неё указывают. Строки реестра **не** перебираем: это
дорого и даёт ложную точность (в реестре модификации написаны по-разному). Реестр можно подключить
позже отдельной задачей, когда появится журнал генераций.

### D6: HTML-only честно помечается

`renderer = "html"` → в UI бейдж «шаблон (HTML), редактирование пока недоступно». Это защищает от
ожидания, что форма уже редактируема.

## Risks / Trade-offs

- [Владелец ждёт редактор, а получит каталог] → это осознанный порядок: сначала видимость, редактор —
  следующий change; в UI прямо написано, что редактирование впереди.
- [Модификации в Аршине не нормализованы] → нормализация + вхождение (D2) и предпросмотр, чтобы
  проверить правило до сохранения.
- [Наследование, которого нет в генерации] → `parent_code` пока влияет на отображение и на будущий
  редактор; генерация продолжает выбирать форму через правила. Это фиксируется в спеке как
  «наследование описывает отношение форм», а не «меняет рендер прямо сейчас».
- [Новая зависимость `d3-force`] → маленькая и без DOM; альтернатива (свой layout) описана в D3.

## Open Questions

- Строить ли `protocol_forms` уже сейчас (D1) или отложить до редактора, а на шаге каталога вывести
  иерархию статически? Решение влияет на миграцию и на объём этого change.
- Нужен ли на графе режим «показать только выбранный тип прибора» по умолчанию (чтобы не рисовать
  весь каталог сразу)?
- Хранить ли редакцию методики (`с изм.№1`) отдельным полем правила или как часть `match_value`?
