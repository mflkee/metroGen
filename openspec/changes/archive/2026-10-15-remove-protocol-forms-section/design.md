# Design

## Context

См. `proposal.md` — Why. Что есть сейчас:

- интерфейс: `ProtocolFormsPage.tsx` (обзор), `src/api/templates.ts`, пункт меню и роут `/admin/templates`;
- API раздела: каталог форм, карточка формы, черновик/публикация/версии/откат, предпросмотр структуры,
  сравнение — `app/api/routes/templates.py` (~600 строк) и `app/schemas/template.py`;
- сервисы структуры: `form_structure.py` (валидация/наложение/diff/предпросмотр) и `form_structures.py`
  (опубликованные структуры + сборка таблицы);
- рендер таблицы из структуры: `_structure_table.html`, обёртки в `pressure.html`/`level_meter.html`,
  `structure_table` в `html_renderer`;
- точки замера из структуры: `GenInput.point_fractions`, `steps_from_fractions`, использование в
  `pressure_common`/`level_meter`;
- БД: `protocol_forms`, `protocol_form_versions`, `template_binding_rules`, `Methodology.template_id`.

**Что генерация реально использует:** `template_rules.resolve_form` (читает `template_binding_rules` и
`Methodology.template_id`) и `TEMPLATES` (пути к HTML-шаблонам). Всё остальное — надстройка раздела.

## Goals / Non-Goals

**Goals:**

- Убрать раздел и всё, что существует только ради него, не тронув выбор формы и рендер протокола.
- Оставить одну честную точку входа в маппинг — API правил.

**Non-Goals:**

- Менять правила, `resolve_form`, `TEMPLATES`, генераторы значений.
- Придумывать замену разделу (владелец: «потом что-то просто придумаем новое»).
- Трогать `html_renderer`/`pdf` за пределами удаления `structure_table`.

## Decisions

### D1: Маппинг остаётся, раздел уходит

`template_binding_rules` + `resolve_form` + `TEMPLATES` — это то, чем генерация выбирает форму; удалять
их нельзя. Удаляется только то, что показывает/редактирует формы: каталог, карточка, структура, версии,
сравнение, предпросмотр структуры, таблица из структуры и точки замера из структуры.

*Альтернатива:* оставить API управления правилами «на всякий случай» — он остаётся, но только правила и
предпросмотр резолва (`/templates/rules`, `/templates/rules/preview`), без каталога форм.

### D2: Таблицы форм удаляются миграцией

`protocol_forms` и `protocol_form_versions` после этого change никто не читает (проверено grep'ом:
единственные читатели — удаляемые роут и `form_structures`). Миграция `DROP TABLE` обратима: downgrade
пересоздаёт схему (данные не восстанавливаются — там были только сид-записи).

*Альтернатива:* оставить таблицы пустыми. Отклонено — «удаляем всё связанное» иначе превращается в
вечный мусор в схеме.

### D3: Проброс явной формы на запуск остаётся

`template_id` в `POST /api/v1/protocols/jobs` и `_template_override` в строках — часть маппинга
(спека `protocol-form-mapping`, сценарий «explicit override is honored»), а не часть раздела. Не трогаем.

### D4: Шаблон снова единственный источник таблицы

`_structure_table.html` и обёртки `{% if structure_table %}` убираются; `structure_table` перестаёт
подставляться. Поведение возвращается к тому, что было до `form-table-columns`, и это покрыто тестом
рендерера (шапка шаблона на месте).

## Risks / Trade-offs

- [Теряем возможность добавлять точки замера/колонки из данных] → осознанно: владелец счёл это Excel'ем
  и попросил придумать новое; API-путь к этому удалён, возврат — отдельным change с нуля.
- [Удаляющая миграция] → удаляются только две таблицы с сид-данными; на staging проверяется
  `alembic upgrade head` и работоспособность генерации.
- [Много удаляемого кода] → диф большой, но он механический: удаление + возврат шаблонов к прежнему
  виду; тесты маппинга и генераторов должны остаться зелёными (это и есть проверка, что генерация не
  задета).

## Open Questions

- Нужна ли когда-нибудь замена разделу (например, «конструктор протокола» вокруг переменных и формул)?
  Решается отдельно; этот change только освобождает место.
