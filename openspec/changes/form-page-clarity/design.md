# Design

## Context

См. `proposal.md` — Why. Термины страницы пришли из модели данных: `match_field` правила стал «осью»,
`template_id` — «формой», `overlay` — «переопределением». Пользователю нужны слова из его работы:
методика, тип, исполнение.

## Goals / Non-Goals

**Goals:**

- Объяснить выбор формы тремя вещами и показать это в интерфейсе.
- Убрать жаргон из подписей, оставив его в коде.
- Дать легенду графу.

**Non-Goals:**

- Менять модель данных или API (переименование — только на уровне текстов).
- Писать отдельную страницу документации (достаточно блока на странице).

## Decisions

### D1: «Признак» вместо «оси»

`match_field` показывается как **признак** — «по чему правило узнаёт прибор». Варианты называются
данными, а не кодом:

| `match_field` | Подпись | Пример |
|---|---|---|
| `mitype_number` | рег. номер типа | `86065-22` |
| `title_keyword` | слова в названии типа | `УРОВНЕМЕР` |
| `methodology_code` | код методики | `МП 1657-7-2024` |
| `modification` | исполнение (модификация) | `901.1`, `FMP51` |

*Альтернатива:* оставить «ось» и добавить сноску. Отклонено — жаргон в подписи читается быстрее сноски
и не требует наведения.

### D2: Вводный блок — три предложения, всегда видимый

Сверху страницы: форма выбирается по методике, описанию типа и исполнению; правила применяются по
приоритету (меньше число — раньше); если ни одно не подошло — встроенная эвристика. Никаких диалогов и
раскрытий: это первое, что видит пользователь.

### D3: Легенда — часть графа

Легенда живёт под графом (там же, где подсказка про зум и перетаскивание) и перечисляет: круг — форма,
квадрат — условие правила, сплошная линия — наследование, пунктир — правило выбирает форму, пунктирная
обводка — форма ещё из HTML-шаблона.

## Risks / Trade-offs

- [Тексты разойдутся с моделью при переименованиях в коде] → в спеке зафиксированы только пользовательские
  слова; таблица соответствия — здесь.
- [Вводный блок займёт место] → три предложения, один абзац; страница и так длинная.

  объясняет минимум.
