# Design

## Context

Сейчас таблицу протокола собирает Python: `app/services/generators/*` (например `pressure_common.py`
строит строки по «красивым» шагам 0..ВПИ), а HTML-шаблон (`app/templates/*.html`) рисует её. Форма —
это файл + код, поэтому «добавить точку замера для модификации» = правка кода и деплой.

Конструктор переносит **форму таблицы** в данные, оставляя **значения** генератору:

```
структура формы (данные)            значения (Python)
─────────────────────────           ─────────────────────────
разделы / таблицы / колонки   +     числа, погрешности, выводы
набор точек замера (строки)
```

## Goals / Non-Goals

**Goals:**

- Правка формы (точки, колонки, заголовки, разделы) без кода и деплоя.
- Наследование с переопределением: база → производные, с распространением правок.
- Сравнение форм и версий, история, откат.
- Предпросмотр на реальной строке до публикации.

**Non-Goals:**

- Менять алгоритмы расчёта значений (погрешности, выводы) — они остаются в генераторах.
- Заменить все HTML-шаблоны сразу — миграция по одной форме.
- Дать редактировать произвольный HTML/CSS (только структура формы).

## Decisions

### D1: Структура формы — JSON с версией схемы

```jsonc
{
  "schema": 1,
  "sections": [
    { "id": "main", "title": "Результаты поверки", "blocks": [
      { "type": "text", "id": "note", "text": "Условия поверки: …" },
      { "type": "table", "id": "points", "columns": [
          { "id": "ref", "title": "Эталон, {unit}" },
          { "id": "si",  "title": "Показания СИ" },
          { "id": "err", "title": "Погрешность" }
      ], "rows": [
          { "id": "p0", "kind": "point", "at": 0,   "label": "0" },
          { "id": "p1", "kind": "point", "at": 0.25 },
          { "id": "p2", "kind": "point", "at": 0.5 },
          { "id": "p3", "kind": "point", "at": 0.75 },
          { "id": "p4", "kind": "point", "at": 1.0 }
      ]}
    ]}
  ]
}
```

`kind: "point"` — точка замера (доля ВПИ или абсолютное значение); генератор подставляет значения по
этим точкам вместо своих «красивых шагов», если структура задана.

### D2: Наследование — оверлей (дельта), а не копия

Производная форма хранит **только переопределения**, ключ — путь в структуре
(`sections/main/blocks/points/columns/err`). Итоговая структура = цепочка родитель → потомок, где
каждое переопределение накладывается поверх.

- правка базы автоматически видна производным, если они не переопределили этот путь;
- «что переопределено» — это и есть список ключей оверлея;
- сравнение — по итоговым структурам, а «наследуемое/переопределённое» — по ключам.

*Альтернатива:* хранить полную копию с флагами. Отклонено — копия рассинхронизируется с базой, и
«правка базы распространяется» перестаёт работать без ручного мержа.

### D3: Версии — иммутабельные снапшоты опубликованного

`protocol_form_versions(form_id, revision, structure_resolved, overlay, published_at, published_by,
comment)`. Черновик — изменяемый оверлей в `ProtocolForm`; публикация фиксирует снапшот. Генерация
берёт последнюю опубликованную версию. Откат = публикация нового снапшота из старой версии (история
не переписывается).

### D4: Generic-рендерер рядом с HTML, с проверкой паритета

Новый `render_structure_html(structure, values, context)` использует те же классы (`.data-table`,
токены темы), что и текущие шаблоны. Для миграции каждой формы — **golden-тест**: отрендерить
имеющуюся HTML-форму и структуру на одних данных и сравнить разметку (нормализованно). Только после
совпадения форма переключается на `renderer = "data"`.

### D5: Генератор получает «форму таблицы» из структуры

`GenInput` дополняется `table_shape` (колонки + точки) из структуры формы; генератор заполняет
значения по этим точкам. Если структуры нет — поведение прежнее (обратная совместимость и миграция
по одной форме).

### D6: Права и черновики

Чтение — всем авторизованным; правка/публикация — `DEVELOPER`/`ADMINISTRATOR` (проверка на backend, не
только в UI). Черновик не влияет на генерацию.

## Risks / Trade-offs

- [Паритет рендера] → golden-тесты на каждую мигрируемую форму (D4); HTML-шаблон остаётся фоллбэком.
- [Схема структуры будет меняться] → поле `schema` + миграции структуры; валидация на backend.
- [Оверлеи станут запутанными] → UI всегда показывает «наследуется / переопределено», а сравнение —
  по итоговым структурам.
- [Генераторы завязаны на свои точки] → переход по одной форме (D5), старые формы не трогаем.
- [Соблазн править HTML напрямую] → вне scope (Non-goals): редактор работает только со структурой.

## Open Questions

- Точки замера: доля ВПИ (`at`) или абсолютные значения? Для уровнемеров (`absolute mm`) может
  понадобиться второй вид — решить на первой миграции.
- Многотабличные формы уровнемера (две таблицы, токовый выход) — это разные формы с общим родителем
  (уже так) или одна форма с несколькими таблицами? Влияет на схему.
- Нужен ли совместный редактор (одновременная правка) или достаточно блокировки формы на время
  черновика?
